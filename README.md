# Muzeel 로컬 재현: 두 예제의 실행 결과

- 실험일: 2026-10-04 (Asia/Seoul)
- 정리일: 2026-10-08
- 대상: 동적 DOM·입력 예제 1개, 정적 장바구니 예제 1개
- 실행 횟수: 예제별 1회
- 원본 프로젝트: [comnetsAD/Muzeel](https://github.com/comnetsAD/Muzeel)
- 기준 커밋: `3dcce3ae78240855015748b5b536deb21a79d721`

## 1. 목적과 현재 확인 수준

Muzeel의 JavaScript 수집, 함수 계측, DOM 이벤트 탐색, 미관측 함수 본문 제거 과정을 로컬 예제 두 개에서 실행했다. 첫 번째 예제에서는 필요한 함수 두 개도 제거됐고, 두 번째 예제에서는 의도한 미사용 함수 하나만 제거됐다.

두 실행 모두 `Complete`까지 도달했고 `run_test.py`의 오류 파일은 비어 있다. 이 보고서는 저장된 원본·최적화 코드, 이벤트 trace, 제거 범위, 완료 기록을 비교한 결과다. 최적화 후 원본과 동일한 시나리오를 재생하는 독립적인 회귀 테스트는 아직 수행하지 않았다. 따라서 첫 번째 사례의 기능 손상은 제거된 본문과 원래 기능 정의에서 판단한 것이며, 두 번째 사례의 모든 기능이 브라우저에서 검증됐다는 의미는 아니다.

이 결과는 작은 인공 예제에 대한 구현 재현이다. 논문의 전체 데이터셋, 성능, 평균 감소율을 재현한 결과로 해석하지 않는다.

## 3. 실험 1: 동적 DOM·입력 예제

기본 버튼을 클릭하면 새 버튼이 생성되고, 새 버튼을 클릭하면 상태 메시지가 바뀐다. 메뉴 열기 후 메뉴 항목 클릭, 이름 입력 기능도 포함한다. `neverCalledFunction`은 의도적으로 어디에서도 호출하지 않았다.

| 함수 | 역할 | 최적화 결과 | 판단 |
|---|---|---|---|
| `updateStatus` | 상태 메시지 갱신 | 유지 | 기대와 일치 |
| `handleInitialClick` | 동적 버튼 생성 | 유지 | 기대와 일치 |
| `handleDynamicClick` | 동적 버튼의 상태 메시지 갱신 | 본문 제거 | 필요한 기능의 잘못된 제거 |
| `toggleMenu` | 메뉴 표시 전환 | 유지 | 기대와 일치 |
| `handleMenuItem` | 메뉴 항목 처리 | 유지 | 기대와 일치 |
| `handleInput` | 입력값을 상태 메시지에 반영 | 본문 제거 | 필요한 기능의 잘못된 제거 |
| `neverCalledFunction` | 의도적인 미사용 함수 | 본문 제거 | 기대와 일치 |
| `DOMContentLoaded` 익명 콜백 | 이벤트 리스너 등록 | 유지 | 기대와 일치 |

### 탐색 기록

저장된 [trace](experiments/dynamic-dom/trace.jsonl)에는 다음 경로가 있다. `baseEvent`는 탐색 시작 상태를 나타내는 내부 이벤트다.

```text
baseEvent
├─ nameInput의 input 이벤트
├─ menuButton 클릭
│  └─ menuItem 클릭
└─ initialButton 클릭
```

`initialButton` 클릭 경로는 있지만 `dynamicButton` 클릭 경로는 없다. 현재 구현은 페이지 진입 시 `HTMLDocumentUtil`로 최초 이벤트 목록을 만들고, 이후에는 그 목록을 사용한다. 버튼 생성 후 새 DOM에서 이벤트 목록을 다시 수집하는 단계가 없어 `handleDynamicClick`의 실행을 관측하지 못했다. 최적화본은 해당 함수를 `function handleDynamicClick() {}`로 만든다.

`handleInput`은 별도 원인으로 조사해야 한다. trace에는 입력 이벤트가 있으나 결과에서는 본문이 제거됐다. 현재 입력 실행은 `move_to_element(...).send_keys("ABCD")`를 사용하며 입력창 클릭·포커스를 명시하지 않는다. 실제 입력이 발생하지 않았을 가능성이 있지만, 저장된 trace는 행동 의도만 담고 있어 포커스 문제를 확정할 수 없다. 입력값·포커스·이벤트 발생 및 원시 함수 로그를 추가 관측해야 한다.

이 두 오류를 모두 동적 DOM 재수집 문제로 설명해서는 안 된다.

## 4. 실험 2: 정적 장바구니 예제

페이지 로딩 시부터 커피 추가, 샌드위치 추가, 장바구니 초기화, 영수증 표시 버튼이 존재한다. `neverUsedAdminDiscount`는 어디에서도 호출하지 않는다.

| 함수 | 최적화 결과 |
|---|---|
| `renderSummary` | 유지 |
| `addCoffee` | 유지 |
| `addSandwich` | 유지 |
| `resetCart` | 유지 |
| `toggleReceipt` | 유지 |
| `DOMContentLoaded` 익명 콜백 | 유지 |
| `neverUsedAdminDiscount` | 본문 제거 |

저장된 [trace](experiments/static-cart/trace.jsonl)는 네 버튼이 모두 최초 상태에서 실행 가능한 것으로 처리됐음을 보여준다.

```text
baseEvent
├─ receiptButton 클릭
├─ resetButton 클릭
├─ sandwichButton 클릭
└─ coffeeButton 클릭
```

원본과 최적화본의 차이는 다음 함수의 본문 제거 한 곳이다.

```javascript
// 원본
function neverUsedAdminDiscount() {
  totalPrice = 0;
  console.log("관리자 전용 할인은 실행되면 안 됩니다.");
}

// 최적화본
function neverUsedAdminDiscount() {}
```

이 사례에서는 소스 비교 기준으로 기대한 함수만 제거됐다. 상품 추가 후 영수증 확인처럼 여러 동작을 연결한 기능 검증은 별도의 회귀 테스트로 남아 있다.

## 5. 로그 해석 시 주의할 점

- `No of events: 4`: 초기 DOM에서 발견된 이벤트 리스너 수다. 함수 개수나 모든 사용자 시나리오 수가 아니다.
- `Parent ...`: 큐에서 꺼낸 이벤트를 선행 이벤트와 함께 재생하는 단계다.
- `Base event triggered`: 내부 시작 이벤트 실행을 뜻한다.
- 반복되는 `No alert`: alert가 없다는 상태 메시지다.
- `2`, `3`, `7` 등의 숫자: 누적된 서로 다른 브라우저 로그 메시지 수다. 함수 실행 로그 외의 메시지도 포함될 수 있다.
- `Complete`: 탐색 루프가 종료됐음을 뜻한다. 독립적인 기능 검증 통과를 의미하지 않는다.

이벤트 처리 코드에는 첫 클릭 이후 최대 두 차례 추가 클릭하는 로직도 있다. 따라서 trace 한 줄을 실제 마우스 클릭 한 번과 동일하게 해석하지 않는다. 원시 브라우저 로그 메시지 전체는 이번 실행의 산출물로 저장되지 않아, 마지막 숫자의 비함수 메시지 구성은 확정할 수 없다.

## 6. 실행 환경과 로컬 변경

당시 기록된 브라우저는 Chrome `154.0.8037.97`, 모바일 에뮬레이션은 375 × 812, pixelRatio 3이었다. Python `3.9.25`, MySQL 8.0과 아래 패키지를 사용했다. [환경 스냅샷](environment.txt)은 보고서 정리 시점에 설치된 버전을 확인한 기록이다.

```text
selenium==4.8.3
selenium-wire==5.1.0
mitmproxy==9.0.1
esprima==4.0.1
PyMySQL==0.10.1
beautifulsoup4==4.12.3
psutil==5.9.8
chromedriver-autoinstaller==0.6.4
setuptools==80.9.0
blinker==1.7.0
```

원저자 코드에 다음 로컬 변경을 적용한 상태에서 실행했다.

1. 이름 기반 `iPhone X` 에뮬레이션을 명시적인 화면 크기와 User-Agent로 변경했다.
2. Selenium Wire 대신 Selenium의 Chrome 직접 프록시와 CDP 추가 헤더를 사용했다.
3. `init_url` 헤더가 없는 Chrome 백그라운드 요청을 프록시 캐시 처리에서 건너뛰었다.
4. `WebDriverWait.until`에 조건 함수를 전달하도록 수정했다.
5. `chrome_debug.log` 파일 읽기를 브라우저 로그 API 수집으로 변경했다.
6. 탐색 예외 발생 시 불완전한 로그로 함수 제거를 진행하지 않도록 수정했다.
7. 탐색 브라우저에서 설치된 ChromeDriver를 재사용하고 일부 백그라운드 통신을 줄였다.

[호환성 패치](compatibility.patch)는 기준 커밋과 보고서 작성 시점의 코드 차이다. 두 번째 사이트의 캐시 수집 후 수정한 목록 빈 줄 건너뛰기와 scraper 오류 로그 초기화도 포함한다. 이 두 수정은 당시 장바구니 수집 결과 이후에 적용됐다. scraper의 `js_count`는 현재 `<script>` 요소 수를 세므로 원저자 코드의 JavaScript 응답 수와 측정 정의가 다르다.

로컬 DB 비밀번호와 개인 경로가 있는 `config.py`, DB 덤프, 브라우저 프로필, `.DS_Store`는 포함하지 않는다. 패치는 전체 프로젝트가 아니며, 위 기준 커밋의 원본 프로젝트에 적용하는 참고 자료다.

## 7. 포함된 근거 파일

각 실험 디렉터리는 다음 파일을 포함한다.

| 파일 | 내용 |
|---|---|
| `index.html` | 예제 HTML |
| `app.js` | 실험 당시 캐시된 원본 JavaScript의 정확한 복사본 |
| `optimized.js` | 생성된 `.m` 파일의 정확한 복사본 |
| `trace.jsonl` | 실행기에서 저장한 선행 이벤트 경로 |
| `event-graph.dot` | 저장된 이벤트 그래프 |
| `removed-ranges.txt` | 원본 소스의 제거 대상 본문 위치 |
| `completed.txt` | URL과 실행 시간 |
| `error-log.txt` | `run_test.py` 오류 기록, 두 사례 모두 빈 파일 |

제거 범위는 Esprima의 소스 위치이며, 파일의 UTF-8 바이트 수와 구분한다. `SHA256SUMS`에는 근거 파일의 해시를 기록했다. 원래 캐시 파일명은 실험 1 `c781510ba2edaced3206099c685435`, 실험 2 `aca6fd1946d4f26a20f12460d400d0`이다.

HTML은 정리 시점의 예제 폴더에서 복사했다. JavaScript는 이후 예제 파일 변경과 혼동하지 않도록 실험 캐시 `.c`를 기준으로 복사했다. 실험을 다시 실행해 과거 산출물을 덮어쓰지 않았다.

## 8. 연구에서 이어갈 작업

먼저 입력 이벤트가 실제 발생했는지 확인해 실행기 문제를 분리하고, 원본과 최적화본에 같은 동작을 재생하는 독립적인 기능 검증을 만든다. 이후 이벤트 실행 후 DOM 이벤트를 다시 수집하는 M+를 구현해 `dynamicButton`을 발견하고 필요한 함수 본문을 보존하는지 비교한다.

각 구현은 동일한 예제·초기 상태·탐색 예산에서 반복 실행해야 한다. 함수 관측 수, 잘못 제거한 함수 수, 파일 크기 감소량, 기능 검증 실패 수를 함께 기록한다. 이번 두 사례는 이 평가를 시작하기 위한 기준 자료이며, AI 에이전트 A/AC의 구현 결과는 아직 포함하지 않는다.
